# 检索对照冒烟记录

本记录是一次可复现的功能与性能冒烟测试，不代表真实业务效果。数据由三篇虚构文档、九个索引切片和随文档编写的 30 条问题组成，标注到目标切片并附预期答案；答案与切片对应关系逐项对照了源 Markdown。标注不是独立人工复核，也不是生产任务基准。每篇文档只有三个切片，不能代表大规模知识库或复杂长文档的实际检索效果。

2026-11-21，在单机 Docker 隔离环境中使用 CPU 版容器和本地缓存的 BGE-M3、BGE reranker，模型预热后顺序执行，K=1，候选数上限为 6。耗时包含单次问题向量化和检索，重排方案还包含重排序；不包含模型冷启动、文档索引及最终回答生成。每题目标切片按文档名和实际 chunk index 标注。

| 方案 | 切片 Recall@1 | MRR@1 | 单问题中位耗时 |
| --- | ---: | ---: | ---: |
| 稠密向量检索 | 0.733 | 0.733 | 382 ms |
| 混合检索 | 0.867 | 0.867 | 382 ms |
| 混合检索 + 重排 | 0.967 | 0.967 | 14,214 ms |

混合检索比稠密检索多命中 4/30 题，reranker 又比混合检索多命中 3/30 题；但 CPU reranker 中位耗时约为 Hybrid 的 37 倍。项目示例将 reranker 默认关闭，超时设为 5 秒，超过后回退到原始检索顺序；本次结果表明，在此 CPU 环境简单提高超时会明显损害交互时延，不建议这样做。样本仍很小且问题与资料共同编写，不能推断其在真实任务中一定有效。后续需要独立核对真实问题和相关切片、扩大文档规模并测试不同 K。逐题结果和本次标签哈希见 [机器可读评测结果](./retrieval-smoke-report.json)。

复现方法见项目 README 的检索评测部分。模型、硬件、负载和文档切分变化都会影响结果。以上检索指标不衡量回答引用正确性或无依据问题拒答率。

后续评测脚本增加了对标注切片内容指纹的校验以及每题召回切片的记录。为保留原始运行证据，本报告的 JSON 未重新生成，记录的是当时的标注文件哈希，因此与加入指纹后的当前标注文件哈希不同，也没有新增的逐题排序字段。

## 问答抽样检查

在上述多切片资料和已建立的图谱上，使用“仅知识库”模式做了 6 条 API 问答抽样：3 条有依据的问题分别询问图书馆借阅上限、商城免运费门槛和工作坊迟到规则；3 条无依据的问题询问管理员薪资、客服电话和报名费金额。一次运行中，6 条均进入 `hybrid_graph` 路由；3 条有依据问题的答案与资料一致并引用目标文档，3 条无依据问题均明确表示知识库无法确定。

这只是一次极小规模的人工抽查，不是稳定性或拒答率的正式评测。抽查中发现 API 的来源列表包含未被答案引用的候选来源；现已改为答案生成后按有效 `[资料N]` / `[图谱N]` 标记筛选响应及会话中保存的来源。若模型没有任何有效引用标记，则保留候选来源，避免误隐藏证据。真实流式请求验证了文档来源事件只保留答案引用的 `library.md`；GraphRAG 请求也验证了最终 `sources` 事件保留被引用的 `[图谱1]` 和 `workshop.md`。

GraphRAG API 抽查前显式重建了隔离知识库的图谱，3 份演示文档生成 63 个实体和 35 条关系。关系问答返回 `hybrid_graph`，回答引用 `[图谱1]`，并同时引用向量文档 `[资料1]`；另一条“举办者与活动”问题的流式回答引用 `[图谱1]`，来源标题为 `workshop.md`。验收时发现两个真实集成缺陷并已修复：图谱来源查询错误访问不存在的 `documents.user_id` 字段，导致 GraphRAG 异常后静默降级；知识库问答路由未传数据库会话，且响应 schema 不接受图谱来源结构。现在文档来源通过知识库所有者关联查询，非流式和流式问答都传递数据库会话，响应与前端也能展示和打开图谱关联文档。问答生成依赖外部模型，结果仍可能随时间变化；以上只是小样本抽查。问答延迟包含检索和外部模型调用，不与上面的检索延迟直接比较。

## 隔离与删除集成检查

2026-11-21 在 `rag-validation` 隔离 Compose 项目中，用两个临时账号经 API 上传短 TXT 文档并等待索引完成。两名用户分别以 dense、sparse、hybrid 模式查询时只召回自己的文档；所有者可读取文档对象，另一用户无法访问。删除文档后，检查确认对应 Milvus 向量行和 MinIO 对象均已清除。另验证不支持的 `.exe` 扩展名会被拒绝。该检查只覆盖两名测试用户和短文本，不替代更广泛的权限审计或并发测试。

另使用临时账号上传一份两页、文字可提取的虚构 PDF，确认异步处理产生页码为 1 和 2 的切片。分别询问两页的事实时，回答给出预期数值，返回的文档来源页码分别为 1 和 2；测试文档随后通过 API 删除，并确认接口不再返回该文档。本次索引在 worker 模型预热后约 8 秒完成；另一次冷启动约 30 秒。两次时间仅供排查参考，不能代表稳定性能或扫描版 PDF 效果。

此前同一文档的多个切片共用引用编号，来源页码却固定为第一个切片，可能使引用跳到错误页。现改为每个检索切片独立编号和保存页码，并通过单元测试检查同文件不同页面不会合并。回答中的编号由模型生成，上述小规模检查不能保证引用语义始终正确。

## 空缓存模型准备检查

2026-11-21 在一个全新的 Docker 命名卷中下载 BAAI/bge-m3（未挂载已有 Hugging Face 缓存），下载完成后关闭网络访问，从该卷加载模型并编码测试文本成功，输出向量维度为 1024。下载容器显式配置了本机可访问的 HTTP/HTTPS 代理；如果部署机器访问 Hugging Face 权重分发域名受限，仍需要先配置有效代理或自行准备模型缓存。此项只验证 Embedding 模型，不表示 Reranker、其他外部服务或全新主机的整个 Docker Compose 已无条件开箱可用。
